# 하자처리 현황 대시보드

아파트 현장의 하자보수 접수·처리 현황을 집계해 팀 단위로 공유하는 웹 대시보드입니다.
HCS(하자관리시스템)에서 내려받은 「전체 하자 목록」 엑셀을 업로드하면 현장별 KPI·추이·장기미처리·피벗 분석을 자동 생성하고,
**사내 게시** 기능으로 팀원 전체가 같은 화면을 실시간으로 열람합니다.

- 배포 주소: https://dongyexn.github.io/report/
- 스택: 단일 `index.html`(vanilla JS) · Firebase Realtime Database + Auth + App Check · GitHub Pages
- 외부 라이브러리: Chart.js, DOMPurify, LZ-String, SheetJS·marked(필요 시점 지연 로드) — 모두 CDN + SRI 고정

---

## 1. 핵심 개념 — 이것만 알면 구조가 보인다

### 데이터 흐름

```
HCS 엑셀 다운로드
   │  (편집자가 업로드)
   ▼
편집자 브라우저 IndexedDB  ←── 원본 하자 행은 여기에만 저장된다
   │  (calc: 기준월 말일 기준 집계)
   ▼
[게시] Firebase RTDB  report/{YYYY-MM}
   │  집계 KPI + 전체 미처리 목록(LZ 압축, PII 마스킹) + 주차/월별 캡처
   ▼
뷰어(팀원) — 게시본을 실시간 구독해 열람
```

**가장 중요한 사실 세 가지:**

1. **원본 데이터는 서버에 없다.** 하자 행 원본은 업로드한 그 PC의 브라우저(IndexedDB)에만 있다.
   서버(RTDB)에는 월별 게시본(집계 + 마스킹된 목록)만 올라간다. 따라서 **업로드·게시하는
   마스터 PC는 한 대로 고정**하고, 그 PC의 브라우저 데이터를 함부로 지우면 안 된다.
2. **편집자 화면 = 로컬 계산, 뷰어 화면 = 게시본.** 편집자가 다른 PC에서 로그인하면 그 PC의
   로컬 원본(없거나 구버전)으로 그려진다. 게시된 그대로 확인하려면 설정 > 「뷰어 시점으로 보기」.
3. **기준월(YYYY-MM)이 모든 계산의 축이다.** 지연일·장기미처리·누계는 전부 기준월 말일 기준.
   월간 보고는 "전월 말일까지"가 기준이므로 업로드 시 기준월 자동값은 전월을 넘지 않는다
   (상단 기준월 칩에서 수동 변경 가능).

### 역할과 권한

| 역할 | 권한 | 부여 방법 |
|---|---|---|
| `editor` | 업로드·게시·처리계획/분석 작성·AI 분석 규칙 수정·사용자 관리 | 기존 editor가 설정 > 계정 관리에서 변경 |
| `viewer` | 게시본 열람 전용(AI 분석 규칙은 열람만) | 회사 이메일(@hdec.co.kr)로 가입하면 자동 부여 |
| `blocked` | 접근 차단 | editor가 지정 |

가입은 `@hdec.co.kr` 이메일 + 메일 인증 필수. 규칙상 **자기 자신에게 editor를 부여할 수 없다**
(권한 상승 차단). 최초 관리자만 Firebase 콘솔에서 `users/{uid}/role = "editor"`를 1회 수동 설정.

### 인수 전 현장

「인수 전 현장」 고정 권역의 현장은 **대시보드 팀 합산(KPI·추이·팀 전체 목록)에서 제외**되지만,
현장 개별 게시본에는 포함되어 뷰어도 개별 현장 화면을 볼 수 있다.

## 2. 사용법 — 뷰어(팀원)

1. 배포 주소 접속 → 회사 이메일로 가입 → 메일 인증 → 로그인.
2. 상단 **기준월 선택기**로 열람할 월 선택(게시월이 하나면 자동).
3. **대시보드**: 팀 합산 KPI. 미처리·장기미처리 카드를 누르면 **팀 전체 목록**(현장 컬럼 포함).
   현장별 현황 표의 증감 배지에 마우스를 올리면 전월→금월 비교가 뜬다.
4. 사이드바에서 현장 클릭 → 현장별 KPI·주차/월별 추이·장기미처리·공가세대 현황.
5. **목록 모달**: 통합검색(Ctrl+F 또는 `/`) · 지연구간 칩 · 열 정렬/필터 · 피벗 · 엑셀 내보내기 ·
   **표 복사**(클립보드 → 엑셀/메일에 Ctrl+V).
6. **피벗**: 행/열/값 칩을 끌어 조합. 팀 전체 목록의 기본은 행=현장 × 열=공종 × 값=건수.
   우측 `%` 버튼으로 전체 대비 비중 표시(기본 꺼짐). 열이 많으면 좌측 라벨·우측 합계 고정,
   가운데만 가로 스크롤.
7. **우클릭 메뉴**
   - 피벗 셀 → **해당 목록 보기**(그 조합의 원본 행으로 드릴다운) · 값 복사
   - 목록 셀 → 이 값으로 필터 · 제외 · 셀 값 복사
   - 목록 헤더 → 열 숨기기 / 숨긴 열 모두 표시 (헤더 경계 드래그 = 열 너비 조절)
   - 대시보드 현장 행 → 현장 화면 · 미처리 목록 · 장기미처리 목록
   - 차트 → 이미지 복사(보고서 붙여넣기용) · PNG 저장
8. 설정 > **사용 안내**에서 이 문서를 앱 안에서 볼 수 있다.
9. 설정 > AI 분석 > 분석 규칙 **열람**으로 현재 팀에 적용 중인 분석 규칙 전체
   (기본 규칙·팀 추가 지침·키워드)를 확인할 수 있다(수정은 편집자 전용).

개인정보: 게시본의 접수내용은 전화번호·이메일·인명 호칭이 마스킹된 상태로 제공된다.

## 3. 사용법 — 편집자(월간 운영 루틴)

1. HCS에서 「전체 하자 목록」 엑셀 다운로드(전 현장 통합본).
2. 업로드 → 현장별 자동 분배·파싱 → 업로드 요약(현장·건수·기간)을 원본과 대조.
3. **기준월 확인** — 자동으로 전월이 잡힌다(엑셀에 당월 접수분이 섞여도 전월 상한).
4. 대시보드·현장 화면 검토 → 장기미처리 표에 **처리계획** 작성(전월 계획 자동 이월) →
   월별 **분석 의견** 작성(AI 분석 생성 버튼 활용 가능 — 아래 4절 AI 참조).
5. 설정 > 사내 게시 > **등록**. 기준월보다 미래인 게시월이 남아 있으면 삭제 제안 토스트가
   뜬다 — 잘못 게시된 월이면 반드시 삭제(뷰어 기준월 선택기에 계속 노출됨).
6. (권장) 설정 > **스냅샷 내보내기**로 읽기전용 HTML 백업 1부 보관.
7. 설정 > **뷰어 시점으로 보기**로 사용자에게 보이는 화면을 최종 확인. F5로 편집 모드 복귀.

## 4. AI 분석 (Gemini)

- 설정 > AI 분석에 **개인 Gemini API 키**를 입력하면 현장 화면의 "AI 분석 생성"과 대시보드
  주요 이슈 재작성이 활성화된다. 키는 이 PC의 브라우저에만 저장된다(키만 개인 저장 — 아래
  규칙 설정과 다름에 주의).
- 접수내용 등 자유 텍스트는 **PII 마스킹 후** 전송된다(전화·이메일·인명 호칭).

### 규칙은 팀 전체 공유, 수정은 편집자 전용

AI 분석 규칙(기본 규칙 수정본·팀 추가 지침·중대하자 키워드)은 RTDB `aiRules` 노드에 저장되어
**팀 전체가 같은 규칙을 실시간으로 공유**한다. 편집자가 저장하면 전 사용자에게 즉시 반영되고,
뷰어는 열람만 할 수 있다(모달 읽기 전용). 각 PC의 localStorage는 부팅 캐시로만
쓰이며 서버 값이 도착하면 덮어쓴다. 설정 카드는 **API 키 / 분석 규칙 전체 보기·편집 /
기본값 복원** 세 항목으로 구성되며, 규칙 관련 입력은 모두 규칙 편집 모달 안에 있다.

- **분석 규칙 전체 보기·편집**(모달): 하드코딩되어 있던 기본 규칙 전체가 항목별로 열거된다 —
  현장 분석(역할·출력 형식 7·내용 규칙 7·후보 주제), 대시보드 이슈(역할·출력 형식 4·내용 4),
  중대하자 의심 추출(키워드 6종 + 장문 기준 글자수). 항목을 수정해 저장하면 해당 항목만
  덮어쓰이고, **비운 항목은 기본값**이 쓰인다(앱 업데이트로 기본 규칙이 개선되면 미수정
  항목은 자동 반영). 수정된 항목에는 "수정됨" 표시가 붙고 항목별·전체 기본값 복원이 가능하다.
  ⚠️ **형식 규칙(HTML·JSON 출력) 그룹에는 경고 배지가 붙어 있다 — 수정하면 분석 결과
  렌더가 깨질 수 있으니 내용 규칙만 조정할 것.**
  중대하자 추출 키워드는 띄어쓰기 유무와 무관하게 매칭되며, 부정문맥 필터와 AI 최종
  판정 로직은 규칙을 수정해도 유지된다.
- **팀 추가 키워드**(모달의 중대하자 그룹 내): 쉼표 구분 목록. 6개 기본 분류에 없는
  새 키워드(예: 화재, 감전, 석면)를 의심 후보로 추출하고, AI에 보낼 접수내용 샘플의
  우선순위 선정에도 반영된다. 저장 시 집계가 즉시 재계산된다.
- **팀 추가 지침**(모달 말미): 기본 작성 규칙 위에 덧붙는 팀 지침을 자유 입력.
  예: "공가세대 항목은 항상 포함", "결로는 원인별로 구분". 내용 규칙에만 우선 적용되며
  출력 형식은 바뀌지 않는다.
- **기본값 복원**(설정 카드의 복원 버튼): 팀 추가 지침·키워드·기본 규칙 수정본을 모두
  비우고 기본 규칙으로 되돌린다. 이것도 팀 전체에 적용된다.
- 참고: 의심 후보는 규칙이 넓게 추출하고, 최종 판정은 AI가 사내 매뉴얼 기준으로 수행하는
  2단 구조다(오탐은 AI 단계에서 걸러짐).

## 5. 수정·배포 절차 (개발 인수인계)

### 파일 구성

| 파일 | 역할 |
|---|---|
| `index.html` | 앱 전체(마크업+CSS+JS 단일 파일, 약 5,600줄) |
| `database.rules` | RTDB 보안 규칙(주석에 설계 의도·수용 리스크 문서화) |
| `update_csp_hash.py` | 인라인 JS 수정 후 CSP 해시 재계산 스크립트 |
| `README.md` | 이 문서 — 앱의 설정 > 사용 안내에서도 이 파일을 그대로 렌더한다 |

### ⚠️ 가장 중요한 규칙 — CSP 해시

`index.html`의 CSP 메타에는 하단 인라인 `<script>` 본문의 **sha256 해시가 고정**되어 있다.
**JS를 한 글자라도 수정하면 해시를 재계산해 교체해야 한다.** 안 하면 앱이 뜨지 않는다.

```bash
python update_csp_hash.py          # 수정 후 반드시 실행
```

주의: 에디터/git이 줄바꿈을 LF↔CRLF로 바꾸면 바이트가 달라져 해시가 깨진다.
`.gitattributes`로 LF 고정 권장.

### 수정 → 검증 → 배포

1. 수정은 외과적으로 — 대규모 리라이트 금지, 기존 주석·설계 의도 보존.
2. 구문 검증(node --check 또는 브라우저 콘솔).
3. 브라우저에서 `index.html?selftest=1` → 자체 점검 전체 통과 확인.
4. CSP 해시 재계산.
5. git push → GitHub Pages 반영(캐시로 수 분 소요 가능 · Ctrl+F5).
6. **계산 로직을 바꿨다면 재게시**해야 뷰어에 반영된다.
7. 인터랙션을 바꿨다면 실제 브라우저에서 해당 화면을 반드시 열어볼 것 — 정적 검사로
   안 잡히는 런타임 오류 이력이 있음(가능하면 Playwright 자동화).

### Firebase 운영

```bash
firebase deploy --only database                                              # 규칙 배포
firebase emulators:exec --only database "node --test tests/database.rules.test.mjs"  # 규칙 테스트
```

- RTDB 최상위 노드: `users` · `report/{YYYY-MM}` · `reportIndex`(게시월→게시시각) ·
  `plans` · `analysis` · `meta` · `siteConfig` · `aiRules`(AI 분석 규칙 팀 공유 —
  `custom` 추가 지침 · `critKw` 키워드 · `ovr/{ruleId}` 기본 규칙 수정본).
  스키마 외 키는 규칙이 거부한다.
- `aiRules`의 `ovr` 키(ruleId)는 `index.html`의 규칙 레지스트리(RULE_DEF·CRIT_DEF) id와
  맞물린다 — 레지스트리에 항목을 추가·개명하면 규칙의 ruleId 패턴 검증도 함께 확인할 것.
- App Check(reCAPTCHA Enterprise) 사용 중. CSP script-src의 Google 계열 호스트
  (`www.google.com`, `www.gstatic.com`, `www.recaptcha.net`, `recaptcha.google.com`,
  `apis.google.com`)가 하나라도 막히면 토큰 재시도 루프로 진입이 멈춘다.
- 사용자 관리는 설정 > 계정 관리에서. 콘솔 직접 수정은 최초 부트스트랩 때만.

## 6. 문제 해결

| 증상 | 원인 | 조치 |
|---|---|---|
| 접속 시 로딩에서 멈춤 + 콘솔 CSP 차단 | 인라인 해시 불일치 또는 reCAPTCHA 호스트 차단 | 콘솔의 차단 URL 확인 → 해시 재계산 또는 script-src에 호스트 추가. 20초 후 안내가 뜨는 워치독 있음 |
| 뷰어 숫자·기준월이 이상함 | 잘못된 월의 구게시본 잔존 | 올바른 기준월로 재게시 → 미래 게시월 삭제 토스트에서 삭제 |
| 목록이 일부만 표시된다는 안내 | 전체 목록(압축) 이전의 구게시본 | 최신 빌드에서 재게시 |
| 집컴(다른 PC)에서 게시 내용이 안 보임 | 편집자 화면은 로컬 원본 기준(설계상 정상) | 설정 > 뷰어 시점으로 보기 |
| AI 분석 버튼이 안 먹음 | Gemini API 키 미입력 | 설정 > AI 분석에 키 입력(개인 키) |
| "규칙 서버 저장 실패" 토스트 | `aiRules` 노드 규칙 미배포(구버전 database.rules) | 최신 `database.rules` 배포(`firebase deploy --only database`) |
| AI 분석 결과 표시가 깨짐 | 형식 규칙(HTML·JSON 출력) 수정 | 규칙 편집 모달에서 형식 규칙을 기본값으로 복원 후 재생성 |
| 규칙을 바꿨는데 다른 PC에 반영 안 됨 | 로그인 전 캐시 화면이거나 서버 저장 실패 | 로그인 상태 확인 → 저장 실패 토스트 여부 확인 → 재저장 |
| 엑셀 업로드가 조용히 어긋남 | HCS 컬럼명 변경 | 업로드 요약과 원본 대조 · 컬럼 매핑 수정(개발 작업) |
| 사용 안내가 안 열림 | README.md 미배포 | 저장소 루트에 README.md 커밋 확인 |

## 7. 하지 말아야 할 것

- **마스터 PC의 브라우저 데이터(IndexedDB) 삭제 금지** — 원본 하자 행이 사라진다.
  삭제·PC 교체 전 HCS 원본 엑셀 보관과 스냅샷 백업 확인.
- JS 수정 후 CSP 해시 갱신 없이 배포 금지(앱 전체 다운).
- `database.rules` 스키마를 앱 수정 없이 단독 변경 금지(양쪽이 맞물림 —
  특히 `aiRules/ovr`의 ruleId 패턴은 앱의 규칙 레지스트리와 쌍).
- 게시 목록의 PII 마스킹 제거 금지 — 입주민 개인정보가 전 팀원에게 노출된다.
- **형식 규칙(OUTPUT FORMAT — HTML·JSON 출력) 수정 금지.** 설정의 규칙 편집에서 경고와
  함께 수정 자체는 가능하지만, 바꾸면 화면 렌더가 깨진다. 내용 규칙·후보 주제·중대하자
  키워드만 조정하고, 형식이 깨졌다면 즉시 기본값으로 복원할 것.
- 규칙 저장은 곧 **팀 전체 적용**임을 잊지 말 것 — 실험적 수정은 저장 전에 팀에 공지하거나,
  월간 게시 직전에는 규칙 변경을 피할 것(분석 결과가 규칙에 따라 달라진다).
